# StampStack code review — v1.3.11

## 1. Verdict

The codebase is in better shape than most solo-dev extensions: strict TypeScript, no `innerHTML` anywhere in the UI, a real compile-time paywall gate, no remote code, minimal permissions, a genuinely privacy-preserving SponsorBlock client (4-char SHA-256 prefix, not the video id), and a filter→DNR pipeline with 179 passing tests over its pure logic. Nothing found is a paywall bypass, a data leak to the page or the network, or a store-policy violation that would get the item pulled today.

But the next store submission should **not** go out as-is. Three things block it: SponsorBlock ships **on by default while the hosted privacy policy and store listing both say it is opt-in** (a copy/behavior mismatch on the exact axis reviewers check), the **live store description is pre-1.3.3 copy that never mentions the paid dark mode, SponsorBlock, or the YouTube toggles**, and the hosted policy + permission justifications declare a `webNavigation` permission the package deliberately does not contain. All three are text edits.

On the code side, the two highest-value fixes are a dead XHR response-rewriting hook (every `json-prune-xhr-response` rule — X/Twitter promoted tweets, Facebook Marketplace ads — is a no-op in every browser) and a latent global-allow hole in the `@@` exception guard that the next `npm run update-lists` could trip. Neither is currently visible to users; both are one-function fixes.

Verified-clean areas worth stating: hostname matching, the k-anonymity story for SponsorBlock, the Dev-unlock compile-time gate, cosmetic-injection XSS surface, DNR regex budget (209/1000), `$badfilter` handling, and dark-mode color math.

## 2. Critical & high findings

No **critical** findings. Five **high**.

### H1 — XHR response rewriting is dead code in every browser
**`src/scriptlets/library.ts:496-517`**

`hookXhrTextTransform` registers its `readystatechange` listener with `{ once: true }`, then early-returns on `this.readyState !== 4`. For any async XHR the sequence is 2 → 3 → 4, so the handler is *invoked* at readyState 2, returns immediately, and `once` removes it before DONE ever fires. `transform()` is never called.

**Failure scenario:** Load x.com with `ubo-filters` enabled. The `/i/api/graphql/.../Home` timeline response contains `promotedMetadata`; `json-prune-xhr-response` is supposed to strip it. The listener was discarded at readyState 2, `responseText` is untouched, promoted tweets render. Same on facebook.com for `MarketplaceFeedAdStory` / `SEARCH_ADS`. Reproduced by bundling the module with esbuild against a spec-shaped fake XHR: 3 events → unpruned; DONE-only → pruned. Blast radius: 29 XHR-rewrite rules (18 `json-prune-xhr-response` + 11 `trusted-replace-xhr-response`), 26 of them non-YouTube, plus the XHR half of `installYoutubeEarlyHooks` (`library.ts:848`). Present since the initial commit.

**Fix:** Drop `{ once: true }`; use a named handler that calls `this.removeEventListener('readystatechange', h)` inside the `readyState === 4` branch (or listen for `loadend`). While there, pass `configurable: true` to the `Object.defineProperty(this, 'responseText', …)` at `library.ts:506` — it currently defaults to non-configurable, so an XHR instance reused across `open()`/`send()` cycles would be pinned to the first transformed body and the redefine would throw into the silent catch.

### H2 — `$all` rules never block top-level navigations; 1,368 badware hosts are inert for `main_frame`
**`scripts/lib/parse-filter.mjs:271`**

`case 'all':` is a no-op with the comment "DNR default = all". That premise is wrong: in Chromium, a rule with neither `resourceTypes` nor `excludedResourceTypes` matches every type **except** `main_frame`. `to-dnr.mjs:446-449` therefore emits `$all` rules with no `resourceTypes`, so the document request is never matched. 1,457 emitted `$all` block rules have no `resourceTypes`; **zero** have them. 1,368 come from `filters/ubo-badware.txt`, which ships `enabledByDefault: true`.

**Failure scenario:** `||buzzadnetwork.com^$all` compiles to `{action:{type:'block'},condition:{urlFilter:'||buzzadnetwork.com^'}}`. A user clicking a link to `https://buzzadnetwork.com/` loads the page normally — only subresources are blocked. uBO blocks the navigation. The same default silently neuters all 41 `$removeparam` rules, which can never strip a tracking param from a top-level URL. `converter.test.mjs:535` asserts a block is emitted but never asserts it covers `main_frame`, so the suite is blind to it.

**Fix:** In `parse-filter.mjs`, make `case 'all':` push `ALL_RESOURCE_TYPES` (already defined at `parse-filter.mjs:38`) into `options.resourceTypes`; do the same for typeless `$removeparam`. Add a converter test asserting `||x^$all` yields a condition whose `resourceTypes` includes `main_frame`, then verify by loading `dist/` and navigating to a `$all` host.

### H3 — The `@@` global-allow guard is enumerative; four inputs still emit a global `allowAllRequests`
**`scripts/lib/to-dnr.mjs:232` (guard) · `test/converter.test.mjs:47` (why it isn't caught)**

`isUniversallyMatchingRegexFilter` is a list of literal regex shapes (`.*`, `.+`, `.{n,}`, `[\s\S]*`, `^https?:\/\/[^\/]+`) with no notion of "contains a literal host anchor". Executing the real modules: `@@/^(.*)$/$document`, `@@/(?:.*)/$document`, `@@/^[^ ]+/$document` and `@@/^https?:\/\/\w/$document` all produce `{action:{type:'allowAllRequests'}, condition:{regexFilter:…, resourceTypes:['main_frame']}, priority:2000}` with no domain scoping. The plain-allow path is open too (`@@/^[^ ]+/`, `@@/(?:.*)/`). Control case `@@/.*/$document` correctly skips, confirming the guard is the only thing standing between these lines and a shipped rule.

**Failure scenario:** `npm run update-lists` pulls an upstream revision containing one of these encodings. Chrome applies the allow to every top-level navigation; it outranks every ordinary block rule (not `$important` ones, priority 3000+), and blocking stops on every site. `npm test` stays 179/179 and nothing in the build reports it. Currently latent: I scanned all 120,396 shipped rules and found exactly one unscoped allow with a `regexFilter`, and it carries a real path literal. But this exact class has been patched **seven times** (PRs #17→#28), each time by adding more literals to the test file.

**Fix:** Replace enumeration with a postcondition. Wrap `convert()` in `converter.test.mjs` so any `allow`/`allowAllRequests` rule must pass an *independent* structural check (non-empty `initiatorDomains`/`requestDomains` after `stripPublicSuffixDomains`, **or** a `urlFilter`/`regexFilter` containing a literal dotted label ≥2 chars that is not a public suffix) — every existing allow test then doubles as an invariant test. Add the same assertion to `scripts/compile-filters.mjs` so a bad list update cannot ship even if the matrix misses a shape.

### H4 — `updateContentScripts` with `excludeMatches: undefined` merges instead of clearing; stale excludes are stranded permanently
**`src/background/service-worker.ts:276` (helper) · `:311` (dark mode) · `:195-196, :238` (YouTube)**
*Found independently by the licensing and service-worker passes.*

`syncOneRegisteredScript` routes an already-registered id through `chrome.scripting.updateContentScripts`, which is a **delta** update — a property is only changed if present. All three call sites pass `excludeMatches: xs.length ? xs : undefined` when the exclude set empties, so the shrink is never applied. `persistAcrossSessions: true` carries the stale value across restarts. (`css` escapes this by accident: the whole script is unregistered when `cssFiles` is empty. The generic-cosmetic script escapes it too: its exclude set is 3,753 patterns from `COSMETIC.networkExceptions` and can never be empty.)

**Failure scenario (worst case, free path):** User allowlists youtube.com from the popup, then re-enables blocking there. `allowlistExclude` goes to `undefined`, `quell-scriptlets-youtube` keeps excluding `*://*.youtube.com/*`, and the MAIN-world YouTube ad hooks **never register on YouTube again for that profile** — until the user happens to also toggle the "sponsored" option off and on, which forces the unregister path.
**Paid path (milder):** last dark-mode force-off override removed → the document_start FOUC shell stays excluded on that host forever, so it flashes white on every load. The dynamic engine is a manifest content script and still darkens the page, so this is a flash, not a permanently light page.

**Fix:** Never pass `undefined` for a property that can shrink — pass the array (empty included). If Chrome rejects `[]`, make `syncOneRegisteredScript` unregister-then-register whenever the desired shape differs from `existing[0]`. A `node --test` around a fake `chrome.scripting` that records the update payload locks this in and unblocks several other findings below.

### H5 — Any `class` mutation rescans the entire subtree with no coalescing or budget
**`src/content/dark-mode-dynamic.ts:389-394` → `:237-251` → `:253-256`**

When `r.attributeName === 'class'` (or the target is `html`/`body`), `collectForReprocess` runs `scope.querySelectorAll('*')` **synchronously inside the observer callback**, adds every descendant to `needsReprocess`, and enqueues them all. No debounce, no root de-duplication, no size cap. The drain then does, per element: `restoreElement` (inline style writes) + a fresh `getComputedStyle` + up to 8 more in `isDarkBackdrop` + `applyPlan` writes.

**Failure scenario:** A site does the extremely common `document.documentElement.className = …` from a scroll handler (unconditional assignment fires a mutation record every event; `classList.toggle(name, force)` only fires on real crossings). On a 10-20k-element page this queues the whole document: ~50-150ms of extra main-thread work per reprocess, spread over 8-20 rAF frames, repeating on every scroll event. Sustained jank or an apparent freeze on a page that is fine without the extension. Not self-oscillating (`isOurStyleWrite` suppresses our own writes), so this is purely cost — but a large, repeatable one. `test/dark-mode-dynamic.test.mjs` covers only the pure color module, so nothing guards it.

**Fix:** Collect mutated roots into a Set, drop roots that are descendants of other queued roots, and move the subtree walk into the existing rAF drain instead of the observer callback. Cap subtree reprocess (above N nodes, re-check only elements already in `saved` — untouched elements have nothing to roll back). This also directly throttles the memory leak in M-tier finding below.

## 4. Missing features & gaps

Ranked by what a paying user notices first.

1. **"I paid $2 and nothing happened."** The post-purchase auto-enable depends on an ExtPay `paidAt` transition that a throwaway instance can consume (`src/background/license.ts:66`). The Options page says "Paid — unlocked" while every page still looks the same until the user finds the global toggle. This is precisely the ticket `docs/SUPPORT_TRIAGE.md` exists to avoid, and **the monetization path has never been verified end-to-end** — `smoke-extpay.mjs` only string-matches a constant.
2. **"The blocked counters say `—` and `n/a`."** The most prominent element in the shipped popup is two dead tiles (`src/popup/popup.ts:65`). Options at least relabels its card "(dev only)"; the popup doesn't. This is what a one-star review is written from.
3. **"I turned blocking off and nothing changed."** The per-site allowlist — advertised in the store listing as the fix for a broken site — does not touch the open tab. The paid dark-mode path already implements exactly the live-refresh pattern that's missing here (`applyDarkModeToOpenTabs`).
4. **No allowlist management UI anywhere.** Dark mode gets a full per-site override manager in Options (`options.html:104-120`); the core ad-blocking allowlist gets nothing (`options.html:123`). Users can't answer `SUPPORT_TRIAGE.md:11`'s own question ("Site allowlisted?") for any site they aren't currently on. Compounded by the subdomain toggle bug above, which is the one case the popup path can't undo.
5. **`$all` badware coverage doesn't reach navigations** (H2). The extension positions itself as a security/badware blocker; the single most important request in the chain isn't blocked.
6. **45.6% of shipped scriptlets are inert** — 827 `nowoif` (popunder defuser), 716 `rmnt`, 655 `aeld`, 359 `no-fetch-if` rules match, get shipped to the page, and get dropped. Implementing the top four recovers ~2,557 rules.
7. **Dark-ink logos vanish on darkened surfaces.** Documented design trade-off of the no-invert approach with an existing per-site escape hatch and a triage lane — noted, not filed. Cheapest interim: treat small `<img src="*.svg">` like inline `<svg>` roots. (Canvas pixel-sampling does not work: cross-origin logos taint the canvas.)
8. **The "already dark → auto force-off" feature is dead code.** Nothing sends `darkmode:autoSkip`, so the popup's auto-off note can never appear and three tested helpers are unreachable — making those tests misleading. Evidence says this was a *deliberate* retirement (`clearBuggyAutoOffOverrides` migration at `service-worker.ts:459-471`), and `siteCanvasIsDark()` covers the need at runtime. **Delete the dead path and fix `AGENTS.md:59`, `docs/DARK_MODE_SITES.md:37`, the design spec and plan** — don't re-wire it.
9. **No in-product filter-list updates.** Lists are frozen per store release. This is an inherent MV3 constraint (uBO Lite has it too) and 118k rules cannot live in dynamic rules — the only real defect here is that `docs/privacy-policy.md:22,40` describes a user-triggered download that has no code path, contradicting the accurate Options copy.
10. **No in-extension "report a broken site" affordance**; the publisher email is two clicks deep behind the Privacy link. `GeneratedMeta.generatedAt` is compiled but never surfaced, so users can't tell how stale their lists are.

### C-HIGH — matchCosmetic rebuilds the entire 6-list merged cosmetic dataset on every cosmetic:get — ~105 ms of blocking SW work per frame, per page load
**`src/engine/cosmetic-match.ts:84`** · perf

`matchCosmetic()` starts with `const merged = mergeCosmeticLists(data, enabledListIds);` (src/engine/cosmetic-match.ts:84). `mergeCosmeticLists` (:40-71) is not a lookup — it materializes the whole dataset from scratch every call: a Set over 29,191 hideGeneric selectors, a `Record<string, Set<string>>` over 28,504 hideSpecific domain keys holding 43,187 selectors, the same for 1,699 unhideSpecific keys, and a fresh concat of 2,217 procedural rules. There is no memoization anywhere: `handleCosmetic` calls `matchCosmetic(hostname, COSMETIC, enabledListIds(settings))` at src/background/service-worker.ts:648, and `enabledListIds(settings)` returns a freshly-built array each time, so even an identity cache would need adding deliberately. I measured it against the real shipped src/generated/cosmetic.json (2.56 MB) on Node v22.23.1 (same V8 as Chrome 120+): `mergeCosmeticLists` averages **104.7 ms** over 10 warm iterations, `matchCosmetic('www.cnn.com')` averages **101.9 ms**, and the part that actually depends on the hostname — the procedural `domainSpecMatches` filter — is **0.17 ms**. So >99% of the cost is rebuilding data that never changes between calls. The caller is `content.ts:103` `sendWithRetry({type:'cosmetic:get', hostname: host})`, and the content script is registered `all_frames: true` + `match_about_blank: true` (src/manifest.json:39-51), so this fires once per frame. The service worker is single-threaded, so the calls serialize behind each other and behind every other message (`scriptlets:get`, `darkmode:get` — which content.ts and dark-mode-smart.ts also send per frame). Note this is *not* the service-worker area's `init()`-per-wake finding: this cost is paid on every page load of every tab, cold worker or not.

**Scenario:** User loads a typical ad-heavy news article with 15 subframes (ad iframes, social embeds, consent frames). Each frame's content script sends `cosmetic:get` at document_start. The SW serializes 16 × ~102 ms = ~1.6 s of pure `mergeCosmeticLists` work on its single thread. The top frame's own request may be queued behind several subframes, so `injectSpecificCss` (content.ts:107) — the site-specific element hiding — does not run until hundreds of ms after the page has started painting, and the ad containers the filters target are visible until then. Every other message queues behind it too: the popup's `popup:get` (opened during load) and each frame's `darkmode:get` wait, which for paid dark mode means the FOUC window in the existing dark-mode finding is widened by the same amount. On a low-end laptop (2-3× slower than my measurement) the same page costs 3-5 s of SW CPU.

**Fix:** Memoize the merge. `COSMETIC` is a module constant and `enabledListIds` only changes when settings change, so cache on the joined id string: `let mergedCache: {key: string; value: CosmeticListData} | null = null;` and rebuild only when `enabledListIds.join(',')` differs. That turns ~102 ms/frame into ~0.2 ms/frame after the first call. Better still, precompute the merged view at compile time in scripts/compile-filters.mjs for the default list set and merge only on non-default configurations. While there, cache `loadSettings()`/`loadLicense()` in SW memory (invalidated by `chrome.storage.onChanged`) — `handleCosmetic`, `handleScriptlets` and `handleDarkModeGet` each do their own uncached `chrome.storage.local.get`, so a 16-frame page also costs ~48 storage IPCs. Add a `node --test` case that asserts two successive `matchCosmetic` calls with the same list ids reuse the merged object.

### C-MEDIUM — Content script runs in about:blank / about:srcdoc frames with an empty hostname: no cosmetics or scriptlets ever apply there, and each frame still costs three service-worker round trips
**`src/content/content.ts:26`** · bug

src/manifest.json:49 sets `"match_about_blank": true` and src/content/content.ts:26 explicitly opts in: `if (location.protocol === 'http:' || location.protocol === 'https:' || location.protocol === 'about:') void start();`. In an about:blank or about:srcdoc frame `location.hostname` is the empty string, and `start()` uses it verbatim (`const host = location.hostname;`, content.ts:85) for `scriptlets:get`, `cosmetic:get` and `youtube:getOptions`. I ran the real compiled dataset through the real matcher (esbuild bundle of src/engine/cosmetic-match.ts against src/generated/cosmetic.json and scriptlets.json): `matchCosmetic('')` returns `hide 0, unhide 0, procedural 0, disableGeneric false` and `matchScriptlets('')` returns 0 rules, versus 2 scriptlets for a comparable real host. So the frame gets nothing — the parent page's site-specific hide selectors, procedural rules and scriptlets are all skipped, even though the frame's effective origin is the parent's. The registered generic stylesheet does not reach these frames either: `syncRegisteredScripts` (src/background/service-worker.ts:218-227) sets no `matchOriginAsFallback`, and grep across src/ returns zero occurrences, so `chrome.scripting`-registered CSS is not injected into about: frames at all. Meanwhile each such frame still pays three SW round trips (`scriptlets:get`, `cosmetic:get`, `youtube:getOptions`), which at ~102 ms per `cosmetic:get` (see the mergeCosmeticLists finding) is pure waste that also delays the real frames' work.

**Scenario:** A publisher's ad slot uses the very common `document.write` pattern: create an `<iframe>` with no `src`, then write the creative into its about:blank document. StampStack's content script runs inside that frame, asks the SW for hostname `''`, gets `{hide: [], unhide: [], procedural: [], scriptlets: []}`, and injects nothing — so a site-specific rule like `example.com##.ad-slot`, or a procedural rule that targets the creative wrapper, never applies inside the frame where the ad actually lives. On a page with 20 such frames the extension additionally burns 60 service-worker messages, ~20 of them ~102 ms `cosmetic:get` calls, producing nothing.

**Fix:** Derive the frame's effective host instead of trusting `location.hostname`: `const host = location.hostname || (location.ancestorOrigins?.length ? new URL(location.ancestorOrigins[location.ancestorOrigins.length - 1]).hostname : '')`, and bail out entirely (`return`) when that is still empty rather than sending three no-op messages. Add `matchOriginAsFallback: true` to the generic-cosmetic registration in syncRegisteredScripts so the generic sheet reaches about: frames too. If inheriting the parent's rules is not wanted, at minimum drop `'about:'` from the content.ts:26 guard and `match_about_blank` from the manifest so the frames cost nothing.

### C-MEDIUM — google-analytics.js redirect surrogate never invokes gtag's event_callback — a globally-applied, default-enabled rule that silently breaks Google's documented outbound-link pattern
**`src/redirects/google-analytics.js:34`** · bug

`src/redirects/google-analytics.js` is mapped from `google-analytics_analytics.js`, `google-analytics_ga.js` AND `googletagmanager_gtm.js` (scripts/lib/redirects.mjs:21-23). I dumped every redirect rule out of src/generated/rulesets and it is served by five rules in `quell-seed` — which is always enabled and cannot be turned off — four of them completely unscoped: `||googletagmanager.com/gtag/js`, `||googletagmanager.com/gtm.js`, `||google-analytics.com/analytics.js`, `||ssl.google-analytics.com/ga.js` (ids 96-99, priority 1500 REDIRECT, no initiatorDomains/requestDomains). `/gtag/js` is the standard GA4 loader, so this surrogate replaces Google's tag script on essentially every site the user visits. The file handles the *legacy* callback contract — lines 15-18 explicitly invoke `hitCallback` on the trailing options object of a `ga()` call — but the gtag half is one line: `window.gtag = window.gtag || function () { window.dataLayer.push(arguments); };` (line 34). In the standard GA4 snippet the page's own inline `function gtag(){dataLayer.push(arguments);}` has already run (it is a synchronous inline script; the tag script is `async`), so `window.gtag ||` keeps the page's version and the surrogate contributes nothing at all for gtag sites. Nothing ever drains `dataLayer` — the file does not wrap `dataLayer.push` (line 33 is a bare `window.dataLayer = window.dataLayer || []`). Google's documented pattern for tracking a click before navigating is `gtag('event', 'click', {transport_type:'beacon', event_callback: function(){ document.location = url; }})`; with the real gtag.js the callback fires (with an `event_timeout` fallback), with this surrogate it can never fire.

**Scenario:** A retailer/publisher wires outbound links or a form submit through GA4: the click handler calls `event.preventDefault()` then `gtag('event','click',{event_callback: function(){ document.location = href; }, event_timeout: 1000})`. StampStack's default-enabled `||googletagmanager.com/gtag/js` rule redirects the loader to this surrogate, the arguments land in `dataLayer` and nothing consumes them, so `event_callback` never runs. The user clicks the link (or 'Continue to checkout'), the default action was prevented, and nothing happens — the page appears frozen on that control, with no console error. The user's only remedy is allowlisting the whole site, which also disables all blocking there.

**Fix:** Wrap `dataLayer.push` in the surrogate instead of only defining `window.gtag`, so the page's own gtag function still routes through you: capture the existing array, replace `push` with a function that stores the entry and, when `args[0] === 'event'` and `args[2]` (or `args[1]`) is an object with a function `event_callback`, calls it via `setTimeout(cb, 1)`. Do the same for `eventCallback` on GTM-style `dataLayer.push({event:..., eventCallback: fn})`. Add a `node --test` case that pushes an event with `event_callback` and asserts the callback runs, mirroring the `hitCallback` behaviour the file already implements at lines 15-18 — the asymmetry between the two is what makes this an oversight rather than a design choice.

### C-MEDIUM — No Incognito handling anywhere: hostnames from private browsing are written to persistent storage, and dark-mode overrides are then listed by name in the Options page
**`src/background/service-worker.ts:773`** · security

src/manifest.json declares no `"incognito"` key, so MV3 defaults to spanning mode: one service worker, one `chrome.storage.local`, shared between normal and incognito windows. `grep -rn incognito src/` returns zero hits — nothing reads `sender.tab.incognito` or `chrome.windows.get(...).incognito` on any write path. Two handlers persist a hostname derived purely from what the user is looking at: `handleToggleSite` (src/background/service-worker.ts:766-778) does `set.add(host)` at line 773 and writes `s.allowlist`; `handleDarkModeSetSiteOverride` (:879-901) does `s.darkModeSiteOverrides[host] = override` at line 895. Both go through `mutateSettings` → `saveSettings` → `chrome.storage.local.set` (src/background/settings.ts:80-82), i.e. straight to disk under the profile's normal (non-incognito) extension storage. The dark-mode map is then rendered verbatim as a visible list of hostnames by `renderDarkOverrides` in the Options page (src/options/options.ts:114-150, `title.textContent = host`), which opens in a normal tab (`options_ui.open_in_tab: true`). The allowlist is worse in a different way — as both the ui and gaps areas established, there is no UI anywhere that lists or clears it, so the entry is persistent and invisible. Chrome's documented expectation for spanning-mode extensions is that they not write incognito-derived data to persistent storage; this one does, on the exact code paths the store listing tells users to reach for.

**Scenario:** User enables StampStack in Incognito (required for it to block there at all) and browses a sensitive site — a clinic, a legal-aid service, an adult site — in a private window. The page breaks, so they follow store/LISTING.md's own advice ('Use the popup to pause StampStack on a site that breaks') and flip 'Block on this site' off. `handleToggleSite` writes that hostname into `stampstack.settings.allowlist` on disk; it survives closing every incognito window, closing Chrome, and reboots, and there is no screen anywhere in the extension that will show it to them so they can remove it. If the user is a paid dark-mode customer and instead flips the per-site dark toggle, `handleDarkModeSetSiteOverride` writes the hostname into `darkModeSiteOverrides`, and it is then printed as plain text in the 'Dark mode site overrides' list on the Options page in a normal window — visible to anyone who later opens the extension's settings on that machine.

**Fix:** Either (a) declare `"incognito": "split"` in src/manifest.json so incognito gets its own worker and its own storage partition — note this needs the SponsorBlock cache, ExtPay license read and DNR sync to be re-verified under two workers — or (b) keep spanning and make the write paths incognito-aware: thread `sender.tab?.incognito` (and `chrome.tabs.query({active:true,currentWindow:true})[0].incognito` for popup-originated calls) into `handleToggleSite`, `handleSetPaused` and `handleDarkModeSetSiteOverride`, and hold incognito-originated allowlist/override entries in an in-memory session map that `syncAllowlist`/`syncDarkModeScripts` union with the persisted set but that is never passed to `saveSettings`. Whichever route, add the behaviour to docs/privacy-policy.md, which currently says nothing about Incognito.

### C-MEDIUM — Service-worker cold start must parse a 3.9 MB bundle before its message listener exists, because both compiled datasets are inlined as JS object literals ahead of it
**`src/background/service-worker.ts:76`** · perf

src/background/service-worker.ts:76-78 does `import cosmeticJson from '../generated/cosmetic.json'` and `import scriptletJson from '../generated/scriptlets.json'`. esbuild inlines these into the bundle as JavaScript object literals (dist/background.js contains exactly one `JSON.parse` in the whole file, and the build-store area already observed a raw property literal `title: "uBlock Origin …"` in it). The two datasets are 2.56 MB + 1.41 MB of source; I read the shipped store artifact's central directory and `background.js` in release/stampstack-1.3.11.zip is **3,897,444 bytes uncompressed** — by far the largest JS file, and 964 KB of the 2.79 MiB package. `chrome.runtime.onMessage.addListener` is registered at service-worker.ts:536, i.e. after all of that in module order, so on every cold start V8 must parse and evaluate ~3.9 MB before a single `cosmetic:get` can be answered. As a floor I measured 92 ms just to `JSON.parse` the two dataset strings on Node v22.23.1; V8 parses object literals materially slower than `JSON.parse` of the equivalent string, so the real per-wake cost is higher. This corrects the service-worker area's verifier, which dismissed the wake-cost finding on the grounds that 'the onMessage listener is registered at module eval' and therefore serves messages concurrently — that argument only holds if module eval is cheap, and here it is the dominant cost. Compounding it, the content-engine area established that 4,229 of 9,278 scriptlet rules (766,905 of 1,414,755 bytes of scriptlets.json) name scriptlets the library does not implement, so a large slice of what is being parsed on every wake is provably dead.

**Scenario:** User has been reading for 40 seconds; the MV3 worker idles out. They click a link. The new page's content script fires `cosmetic:get` at document_start, which starts the worker — and the response cannot be produced until V8 has parsed and evaluated 3.9 MB of script, because the `onMessage` listener does not exist until the end of that module. Only then does the ~102 ms `mergeCosmeticLists` run (see the first finding). The result is that site-specific element hiding on the very first page after every idle-out is delayed by the sum of both, hundreds of milliseconds on a fast machine and well over a second on a low-end one — which is exactly the window in which ad containers are visible. This repeats dozens to hundreds of times a day.

**Fix:** Stop inlining the datasets into the worker bundle. Load them lazily and off the module-eval path: ship cosmetic.json/scriptlets.json as files in dist/ and read them with `fetch(chrome.runtime.getURL('generated/cosmetic.json')).then(r => r.json())` behind a memoized promise that `handleCosmetic`/`handleScriptlets` await — `JSON.parse` is much faster than object-literal evaluation and, more importantly, it moves the cost off the path that gates listener registration. As a cheap first step that needs no restructuring, apply the content-engine area's compile-time filter for unsupported scriptlet names, which removes ~54% of scriptlets.json outright. Also move the `chrome.runtime.onMessage.addListener` registration to the very top of the module so it is installed before any heavyweight initialization.

### C-LOW — Every store package ships a 541 KB generic-cosmetic.css that nothing ever loads, and its constant has zero consumers
**`scripts/build.mjs:167`** · robustness

scripts/compile-filters.mjs:364 writes a combined `src/generated/generic-cosmetic.css`, and scripts/build.mjs:167-169 copies it into `dist/generated/generic-cosmetic.css`. Nothing loads it. `syncRegisteredScripts` (src/background/service-worker.ts:214-218) builds its `css` array from each list's `genericCssFile`, i.e. the per-list files under `generated/generic-cosmetic/` (easylist.css, easylist-cookie.css, …), which are copied separately at build.mjs:161-166. The constant that names the combined file, `GENERIC_CSS_PATH = 'generated/generic-cosmetic.css'` (src/shared/constants.ts:38), has exactly one occurrence repo-wide — its own definition; `grep -rn GENERIC_CSS_PATH src/ scripts/` returns nothing else. So it is a byte-for-byte duplicate of content already in the package: ~4.6% of the 2.79 MiB upload and 541 KB of extra disk per install, permanently.

**Scenario:** Every user who installs or auto-updates StampStack downloads and stores 135 KB compressed / 541 KB on disk of CSS that no code path can ever inject — a straight duplicate of the six per-list sheets sitting next to it in the same package. A Chrome Web Store reviewer inspecting the package for the (already-rejected-once) single-purpose review sees a large unreferenced stylesheet with no explanation, and the maintainer following docs/RELEASE_CHECKLIST.md has no signal that it is dead.

Add an assertion to scripts/package.mjs's validateDist() that every file under dist/generated/ is either listed in meta.json (`rulesetFile` / `genericCssFile`) or referenced by name in dist/background.js, so unreferenced payload cannot silently re-enter the package.

## 7. Refuted claims (kept for the record)

Six findings were killed by the adversarial verifiers. Do not re-file them:

- **[service-worker] mergeSettings does not validate allowlist element types; one non-string entry throws inside normalizeHostname and kills all cosmetic filtering**
  - The code observation is accurate — src/background/settings.ts:67 copies allowlist elements unvalidated while every scalar field is type-checked, and normalizeHostname (src/shared/hostname.ts:88) would indeed throw TypeError on a non-string, cascading through isAllowlistedHost (209-215) into handleCosmetic — but I could not find any producer of the required input state, which is what the finding turns on. The only writer of `allowlist` in the whole extension is handleToggleSite (service-worker.ts:766-778), which builds the array from `normalizeHostname(...)` filtered by isSafeAllowlistHost, i.e. always strings; I grepped src/options for allowlist editing and there is none (only prose in options.html:80), and there is no settings import/paste feature anywhere. Storage is chrome.storage.local, not storage.sync, so there is no cross-device merge or partial-sync path, and no other extension can write it. The reviewer's premises — "corrupt write, a partially-synced blob, or a future/older build" — are speculation, not a specific input/state. Note also that the one place raw stored settings reach a consumer without mergeSettings (src/content/content.ts:74-79 → youtubeOptsFromSettings) already guards the shape it can plausibly encounter, `settings.allowlist ?? []` (src/content/youtube-ui.ts:106). The suggested filter is cheap, harmless hardening and I would take the patch, but as a reported defect it has no reachable failure scenario.
- **[dark-mode] `isDarkBackdrop` gives up after 8 ancestors and defaults to "dark", lightening text over light photo backdrops**
  - The code reads as described (`src/content/dark-mode-dynamic.ts:84` caps the walk at 8, `:113` returns true on fall-through), but the conclusion is wrong on three counts. (1) The reviewer misreads the comment: `:80-82` states the policy for a url()-image or unparseable surface that is FOUND, and that policy IS implemented (`:95-98` returns false on url(), `:106-109` returns false on unparseable). Nothing in the comment claims a policy for budget exhaustion, so there is no self-contradiction. (2) The chosen fallback is the *safe* one, not the unsafe one. The dominant real-world case for exhausting the budget is text nested more than 8 levels below the last painted background — where that background is `body`/`html`, which the engine darkens (`remapBackgroundColor` in `src/shared/dark-mode-dynamic.ts:100-111` darkens anything with lum >= 0.15, and `isDarkBackdrop:100-104` correctly notes any opaque parseable surface ends up dark either way). Returning `false` there, as proposed, would leave the site's near-black text on our charcoal canvas — invisible text on a huge fraction of deeply-nested pages. The proposed fix is a far worse regression than the bug it targets. (3) The claimed failure requires ≥8 *consecutive fully transparent* ancestors between dark text and a `url()` hero — any opaque ancestor in between short-circuits correctly, `batchBg` memoizes ancestors already resolved in the batch, and dark text over a bright photo hero is itself an uncommon design (sites normally set light text there, which `remapForegroundColor` keeps via the FG_KEEP_LUMINANCE=0.45 gate). I could not construct a realistic reachable case.
